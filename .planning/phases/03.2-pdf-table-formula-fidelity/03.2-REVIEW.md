## Warnings

### WR-01: `zip(batch_segs, results)` silently drops segments when LLM returns fewer items than expected

**File:** `backend/src/app/workers/translate_worker.py:433`
**Issue:** `zip` truncates silently when `results` is shorter than `batch_segs`. `translate_batch` is expected to return exactly `len(batch_segs)` items, but if the LLM response is malformed or the translator strips entries, the remaining segments are silently absent from `translated_map`. The reassembler falls back to `source_text` for those segments, so the output is not corrupted — but the silent drop bypasses the overflow/flag pipeline entirely and offers no diagnostic signal.
**Fix:** Assert or log a mismatch after the zip loop:
```python
if len(results) != len(batch_segs):
    log.warning(
        "batch_result_count_mismatch",
        job_id=job_id,
        batch=batch_id,
        expected=len(batch_segs),
        got=len(results),
    )
for seg, translated in zip(batch_segs, results):
    translated_map[seg.id] = translated
```

### WR-02: `table_cell` segments accumulate spurious `multi_column_degraded` flags when the structural position contains `col`

**File:** `backend/src/app/workers/translate_worker.py:607-619`
**Issue:** The degraded-page filter is:
```python
_degraded_seg_ids = {
    s.id for s in segments
    if "col" not in s.structural_position
    and s.structural_position.startswith("page.")
}
```
`table_cell` structural positions look like `page.0.table.0.row.0.col.0` — the substring `col` is present, so they are correctly excluded from `_degraded_seg_ids`. However, this relies on the coincidental overlap of the `col` token in the table position format. If the position format ever changes (e.g. `page.0.table.0.row.0.cell.0`), table_cell segments would be incorrectly flagged as `multi_column_degraded`. The logic is currently correct but fragile.
**Fix:** Tighten the predicate to explicitly exclude non-text segment kinds, or make the column check more precise:
```python
_degraded_seg_ids = {
    s.id for s in segments
    if s.structural_position.startswith("page.")
    and s.kind == "text"           # only text segments can be degraded-column
    and "col" not in s.structural_position
}
```
This eliminates the implicit reliance on `col` appearing in `table_cell` positions.

## Info

### IN-01: `SegmentORM` has no `kind` column — `kind` is pipeline-internal only

**File:** `backend/src/app/db/models.py` (referenced from `backend/src/app/workers/translate_worker.py:352-369`)
**Issue:** `Segment.kind` (`"text"` | `"table_cell"` | `"math_passthrough"`) is carried through extraction, translation filtering, and reassembly, but is never written to the DB. `SegmentORM` has no `kind` mapped column. This means the review UI and the `/jobs/{id}/segments` API cannot distinguish cell vs. body vs. passthrough segments, which limits future segment-level display features.
**Fix:** If kind-aware segment display is in scope for Phase 03.2+, add a `kind` column to `SegmentORM` and a matching Alembic migration. If it remains pipeline-internal by design, document this explicitly in the model to prevent future confusion:
```python
# kind is intentionally pipeline-internal (not persisted).
# Reassembler dispatch uses Segment.kind (dataclass); ORM model has no kind column.
```

### IN-02: `import logging` deferred inside `except` block in extractor

**File:** `backend/src/app/pipeline/pdf/extractor.py:257`
**Issue:** `import logging as _logging` is placed inside the `except` block. While Python caches module imports (no repeated disk I/O), the pattern is inconsistent with the rest of the codebase that uses top-level imports and `structlog`. It also means the import does not appear in static analysis of the module's dependencies.
**Fix:** Move `logging` import to the module top-level, or better, use `structlog` (already used in `reassembler.py`) consistently:
```python
import structlog
_log = structlog.get_logger()
# ...
except Exception as _table_exc:  # noqa: BLE001
    _log.warning("find_tables_failed", page=page_num, error=str(_table_exc))
```

### IN-03: Module-level `import os`, `import re`, `from pathlib import Path` placed mid-file in test

**File:** `backend/tests/pipeline/test_pdf_roundtrip.py:132-134`
**Issue:** `import os`, `import re`, and `from pathlib import Path` appear at line 132, after the first block of test functions. Python resolves these correctly at load time, but placing standard-library imports mid-file (not at the module top) violates PEP 8 / ruff import ordering and may confuse static analysis tools.
**Fix:** Move these three imports to the top of the file with the existing `import pytest`:
```python
import os
import re
from pathlib import Path

import pytest
```
