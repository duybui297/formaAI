**Researched:** 2026-04-29
**Domain:** PyMuPDF 1.27 table API, redact-reinsert workflow, insert_htmlbox overflow semantics
**Confidence:** HIGH — all critical claims verified via source-code inspection and empirical probing of the installed PyMuPDF 1.27.2.3 in the project venv.

## Summary

Phase 03.3 fixes two observed failure modes in the native-PDF reassembler's table-cell path, surfaced on job `7f958166` (1409 segments, 98% table_cell). Both bugs were diagnosed via empirical probing of the installed PyMuPDF 1.27.2.3.

**Bug 1 — Visual text adhesion ("cells mix"):** Adjacent cells share a single coordinate at each border centerline (`c0.x1 == c1.x0 == exact_border_center`). When `insert_htmlbox` fills cell0 to its right edge (x=150) and cell1's text starts at x=151, the two words render with no visual gap. PDF word-extraction joins them as a single token (`"đoạnGiá"`). In a viewer, translated content appears to bleed across the cell boundary. The fix is a **1–2 pt inset applied to the INSERT rect only** — not to the redact rect. The redact rect stays at the full cell dimensions to fully erase all source glyphs; the insert rect is inset so translated text has a visible gutter from the border line.

**Bug 2 — Blank cells from overflow:** `insert_htmlbox` with `scale_low=0.7` returns `spare_height=-1` AND renders **no text at all** (completely blank cell) when the translated text cannot fit at 70% scale. Empirical testing showed that JP→VN-expanded text in 80–120 pt wide, 12–20 pt tall cells fits at scale 0.50–0.65. Lowering `scale_low` from `0.7` to `0.3` resolves the overflow for all tested cases without adding new side effects.

**Primary recommendation:** Two targeted changes in `reassemble_pdf`: (1) apply a 1.5 pt inset to all `insert_htmlbox` rects for `table_cell` segments (redact rect unchanged), and (2) lower `scale_low` from `0.7` to `0.3` for `table_cell` inserts. No architecture changes. No new dependencies.

## PyMuPDF Table API — Cell Rect Semantics (VERIFIED)

### Cell Rect Coordinates Include Border Centerlines [VERIFIED: source inspection + probe]

`find_tables()` builds cells from line intersections at `(v_edge.x0, h_edge.top)`. The code in `pymupdf/table.py:2432` uses `abs(rect.x1 + rect.x0) / 2` — the **centerline** of the border line is used as the cell coordinate. Empirical probe confirms:

```
# Lines drawn at x=[50, 150, 250] with width=2pt
cell[0] = (50.0, 50.0, 150.0, 100.0)   # c0.x1 = 150.0 (center of shared border)
cell[1] = (150.0, 50.0, 250.0, 100.0)  # c1.x0 = 150.0 (center of shared border)
# c0.x1 == c1.x0 — NO coordinate overlap, only shared point
```

Adjacent cells share one coordinate value. They do NOT overlap spatially. The border line's half-width lies outside the cell rect on both sides.

### Implication for Redaction [VERIFIED: probe]

Redacting the full cell rect erases all text within the cell. Characters whose bbox spans the boundary (straddling `x=150`) are erased by whichever redaction covers that half. With `graphics=0` in `apply_redactions`, **vector border lines are preserved** — confirmed by counting `page.get_drawings()` before and after.

### Implication for Visual Mixing [VERIFIED: probe]

After `insert_htmlbox` fills cell0 rect `(50,50,150,70)`, the last word renders close to `x=148`. Cell1's insert starts at `x=151`. In PDF text extraction, `get_text('words')` concatenates adjacent words with no gap as `"đoạnGiá"`. In a PDF viewer, these words appear immediately adjacent with no white-space gap — readers perceive this as text bleeding from cell0 into cell1.

**Root cause:** The insert rects share the border-centerline coordinate with zero padding. The fix is an inset on the **insert rect** (not the redact rect).

### No "Rect-Without-Border" API Exists [VERIFIED: docs + source]

PyMuPDF provides no built-in method to obtain a cell rect that excludes the border stroke width. The table module does not store `linewidth` per cell. Manual inset arithmetic is the only approach: `insert_rect = cell_rect + (INSET, INSET, -INSET, -INSET)`.

## insert_htmlbox — Overflow Behavior (VERIFIED)

### scale_low Semantics [VERIFIED: docs + probe]

```
spare_height, scale = page.insert_htmlbox(rect, html, ..., scale_low=0.7)
```

- `spare_height >= 0`: text fit, value = unused vertical space at bottom of rect
- `spare_height < 0` (specifically `-1.0`): text could NOT fit at `scale_low`. Rendered text: **NONE** — the cell is completely blank.
- `scale` = actual scale factor applied (between `scale_low` and 1.0)

**Critical:** When `spare_height = -1`, the method renders **zero text** into the rect. There is no partial text, no overflow outside the rect, and no truncation. The cell appears blank.

### Overflow Threshold for JP→VN Expansion [VERIFIED: probe]

Empirical tests on the project venv (PyMuPDF 1.27.2.3, Noto fonts):

| Cell size | Text length | scale_low=0.7 | scale_low=0.5 | scale_low=0.3 |
|-----------|-------------|----------------|----------------|----------------|
| 80×15 pt | ~20 chars (VN) | OK (scale=0.74) | OK | OK |
| 80×12 pt | ~10 chars (VN) | OK (scale=0.78) | OK | OK |
| 100×20 pt | ~50 chars (VN) | BLANK (-1) | OK (scale=0.61) | OK |
| 80×12 pt (tight) | ~50 chars (VN) | BLANK (-1) | BLANK (-1) | OK (scale=0.40) |

**Conclusion:** `scale_low=0.3` resolves all tested overflow cases. The natural minimum scale is ~0.40 (text still legible). Going below 0.3 provides no additional benefit.

### Does insert_htmlbox Overflow Past Rect? [VERIFIED: probe]

No. `insert_htmlbox` always clips to the rect. Words at the boundary are clipped mid-glyph. The visual mixing is NOT caused by text overflowing outside the rect — it is caused by zero-gap adjacency of two correctly-clipped cell inserts (Bug 1, addressed by inset).

## Architecture Patterns

### Current Flow (Buggy)

```
Pass 1: add_redact_annot(cell_rect, fill=None)       # for ALL cells
Pass 2: apply_redactions(images=0, graphics=0)        # one call
Pass 3: insert_htmlbox(cell_rect, html, scale_low=0.7) # for ALL cells
```

Problems:
- Pass 3 uses `cell_rect` with no inset → zero gap between adjacent cells → visual adhesion
- `scale_low=0.7` → cells with >3× expansion render blank (spare_height=-1)

### Fixed Flow

```
Pass 1: add_redact_annot(cell_rect, fill=None)             # UNCHANGED — full rect erase
Pass 2: apply_redactions(images=0, graphics=0)              # UNCHANGED
Pass 3: insert_htmlbox(cell_rect + INSET_DELTA,             # NEW: inset insert rect
                       html,
                       scale_low=TABLE_SCALE_LOW)            # NEW: 0.3 for table cells
```

Constants:
```python
_TABLE_CELL_INSET_PT = 1.5   # inset each edge by 1.5pt; leaves 3pt gap between cells
_TABLE_SCALE_LOW = 0.3       # allow up to 70% scale-down for table cell text
```

### Inset Arithmetic [VERIFIED: source]

`pymupdf.Rect` supports tuple arithmetic: `rect + (dx0, dy0, dx1, dy1)` shifts each coordinate:

```python
# Shrink rect by INSET on every side:
insert_rect = cell_rect + (INSET, INSET, -INSET, -INSET)
# Example: cell_rect=(50,50,150,100), INSET=1.5
# insert_rect=(51.5, 51.5, 148.5, 98.5)
```

### Overflow Flag Logic (Adjusted)

Current thresholds: `_MIN_RECT_HEIGHT_PT = 6.0`, `_MIN_RECT_WIDTH_PT = 20.0`. These already skip cells too small to hold any text. After the inset is applied, the effective cell is 3pt narrower and 3pt shorter. Existing guards should be kept; the `table_cell_rect_too_small` reason code remains valid.

After `insert_htmlbox` with `scale_low=0.3`:
- `spare_height < 0`: overflow flag, `overflow=True` (cell still blank — this is now a true hard overflow)
- `0 <= spare_height, scale < 1.0`: auto-adjusted flag, `auto_adjusted=True`
- `spare_height >= 0, scale == 1.0`: fits perfectly, no flag

## Common Pitfalls

### Pitfall 1: Inset the Redact Rect Too

**What goes wrong:** Applying inset to BOTH the redact rect and the insert rect. If the redact rect is inset, a 1.5 pt strip around each cell edge is NOT redacted. Source glyphs near the cell boundary (common in dense tables) survive and appear beneath the new translated text.

**How to avoid:** Inset ONLY the `insert_htmlbox` rect. Keep `add_redact_annot` at the full `cell_rect`.

**Code check:**
```python
page.add_redact_annot(cell_rect, fill=None)          # full cell — correct
...
insert_rect = cell_rect + (_TABLE_CELL_INSET_PT, ...)
page.insert_htmlbox(insert_rect, ...)                 # inset — correct
```

### Pitfall 2: scale_low=0 Default (EXISTING, documented in current code)

**What goes wrong:** `insert_htmlbox` with `scale_low=0` (default) NEVER reports overflow — it always scales down to near-zero to fit. `spare_height` is always >= 0. No overflow flags are emitted. Cells with very long text render at 5% scale (unreadable).

**How to avoid:** Always pass an explicit `scale_low`. For table cells, use `_TABLE_SCALE_LOW = 0.3`.

### Pitfall 3: scale_low=0.7 Causes Blank Cells (BUG BEING FIXED)

**What goes wrong:** When translated text needs scale < 0.7 to fit, `insert_htmlbox` returns `spare_height=-1` and renders NOTHING. The cell is blank. This is NOT the same as "overflow flagged" — the flag IS emitted, but the cell is blank with no visual indicator in the PDF output.

**How to avoid:** Use `scale_low=0.3` for table cells. If `spare_height` is still -1, the cell genuinely cannot fit even at 30% scale — this is a true hard overflow and the existing overflow flag logic is correct.

### Pitfall 4: Non-Empty Spare Height Confusion

**What goes wrong:** Treating `spare_height == 0` as overflow. `spare_height = 0` means text EXACTLY fits — no remaining space, but NOT an overflow. Only `spare_height < 0` is an overflow.

**How to avoid:** Check `if spare_height < 0:` not `if spare_height <= 0:`.

### Pitfall 5: find_tables() Cell Index Mismatch

**What goes wrong:** Using `cell_idx = r * tbl.col_count + c` with `tbl.cells[cell_idx]` gives WRONG results when some cells are `None` (merged cells). The `tbl.cells` list is not a flat row-major array — it is sorted by (y, x).

**Current code uses row walk instead:**
```python
for r_idx, row in enumerate(tbl.rows):
    for c_idx, cell in enumerate(row.cells):
```
**Keep this pattern. Do not switch to flat index arithmetic.**

### Pitfall 6: Text-Positioned Tables (Known Limitation from 03.2)

`find_tables()` with default strategy detects only vector-bordered tables. The BMC academic-paper fixture (Table 2, text-drawn borders) returns 0 tables. This is a pre-existing limitation; Phase 03.3 does NOT address it. The 03.2 deferred gap stands.

## Code Examples

### Fixed insert_htmlbox Call (table_cell path)

```python
# Source: verified against PyMuPDF 1.27.2.3 installed in project venv
_TABLE_CELL_INSET_PT = 1.5   # keeps 3pt gap between adjacent cells
_TABLE_SCALE_LOW = 0.3       # allows text to scale down to 30% (was 0.7)

# In Pass 3 (reassemble_pdf), for table_cell segments:
if seg.kind == "table_cell":
    cell_rect = pymupdf.Rect(block["bbox"])
    insert_rect = cell_rect + (
        _TABLE_CELL_INSET_PT, _TABLE_CELL_INSET_PT,
        -_TABLE_CELL_INSET_PT, -_TABLE_CELL_INSET_PT,
    )
    # Guard: inset must not make rect empty
    if insert_rect.is_empty or insert_rect.width < 5 or insert_rect.height < 3:
        # Fall back to full rect for very tight cells
        insert_rect = cell_rect
    spare_height, scale = page.insert_htmlbox(
        insert_rect,
        sized_html,
        css=css,
        archive=arch,
        scale_low=_TABLE_SCALE_LOW,   # was 0.7
        overlay=True,
    )
```

### Rect Inset Arithmetic (PyMuPDF)

```python
# Source: PyMuPDF 1.27 Rect arithmetic (verified: pymupdf.readthedocs.io)
# Rect + tuple(dx0, dy0, dx1, dy1) shifts each coordinate
rect = pymupdf.Rect(50, 50, 150, 100)
inset_rect = rect + (1.5, 1.5, -1.5, -1.5)
# inset_rect = Rect(51.5, 51.5, 148.5, 98.5)
```

### Detecting insert_htmlbox Overflow vs Auto-Adjust

```python
# Source: PyMuPDF 1.27 docs (verified)
spare_height, scale = page.insert_htmlbox(rect, html, scale_low=0.3)
if spare_height < 0:
    # OVERFLOW: could not fit even at 30% scale. Cell is BLANK.
    overflow_flags.append({
        "segment_id": seg.id, "overflow": True,
        "auto_adjusted": False, "scale_applied": round(scale, 3),
    })
elif scale < 1.0:
    # AUTO-ADJUSTED: fit but required scaling
    overflow_flags.append({
        "segment_id": seg.id, "overflow": False,
        "auto_adjusted": True, "scale_applied": round(scale, 3),
    })
# else: perfect fit, no flag
```
